## 1. 改造目标

实施说明：保留本方案的设计理由和场景标准。当前实现包括草稿顺序保存与退出保护、日期范围回顾、日间问题上下文、反馈方向快照、首页行动编辑、完整历史方向与来源说明。第四轮补齐步骤恢复、待回看标记、可选修改原因和多批次晨稿归档，SQLite 升级到 v13。观察不自动绑定归档批次。运行证据与尚未验证的设备场景分别记录在交付报告中。

让 App 帮用户经历这条思考与实践路径：

**看见自己正在维持的生活 → 探索行为在保护什么 → 选择真正想建设的生活 → 尝试相符的日常行动 → 从结果中学习并修正。**

作者在 I–IV 中讨论身份、隐藏目标和感知框架，在 V 中讨论行动、感知、比较和再次行动，在 VI 中给出晨间、日间、晚间流程，在 VII 中用六组件组织注意力。产品要把这些关系变成用户能经历的过程。

晨间写出的“我害怕被评价”可以成为一个解释；白天的具体行为可能支持它，也可能显示还有其他因素；晚间据此选择方向和行动；后续结果继续帮助用户核对。App 负责提问、保存、带回材料和帮助比较，解释与选择由用户完成。

完成问卷、记录次数和界面停留时间只能说明操作。验收不能要求用户产生强烈痛苦、获得深刻洞见或证明身份已经改变。

## 2. 先修正检查报告的使用方式

原报告的交互缺陷、保存风险、材料回顾问题和越界文案仍有处理价值。产品判定需要拆开：

| 类别 | 具体问题 | 处理原则 |
|---|---|---|
| 已确认的功能缺陷 | 反馈首次输入后保存按钮不更新 | 必须修复并做交互回归 |
| 可靠性缺口 | 退出时待保存内容、失败仍报成功、跨日回顾遗漏 | 核对运行行为，修复并验证 |
| 方法表达问题 | 次数被解释为心理变化，系统替用户确定归因，概念混用风险 | 修正文案和上下文，让用户能思考与核对 |
| 体验改进 | 日间直接回看晨稿、关提醒后仍能练习、历史详情、继续草稿 | 按使用场景设计，不宣称作者规定了这些入口 |
| 可选工程与产品扩展 | 反思批次外键、步骤索引、修改原因、再次尝试按钮 | 只有解决实际问题时才引入 |

以下判定需要收回或限定：

- 未同时展示全部目标，不足以证明缺少反馈方法；用户能取得相关方向并比较结果即可。
- 没有“再次尝试”按钮，不足以证明不能再次行动；下一次调整能被带回行动场景即可。
- 没有独立理论页，不足以证明没有理解原文；在关键情境中的简短提示也能表达方法。
- 没有批次外键、步骤恢复或修改原因字段，不等于违反原文。
- 晚间探索内部模式本来来自原文，不能把这项探索整体判为教条。

报告 §8.3 表格可作为待核对清单，不能作为每项都必须新增页面和字段的开发命令。交付后的报告应分别描述“内容支持”“流程可用”“哪些运行场景已验证”，不用功能数量计算完整度。

## 3. 保留的产品基础

保留晨间 14 问、日间六问与追加三问、晚间综合以及六组件。保留首页中枢导航、一个突出的最小启动行动、本地保存与备份、低负担体验，不增加常驻底部导航。

六组件仍为：反愿景、愿景、一年目标、一月项目、每日杠杆、价值约束。身份陈述、最小启动行动和环境避坑规则有各自作用，不替代六组件。

原文锋利的提问继续保留其探索作用。需要明确区分作者提出的问题、用户写出的解释、系统根据记录能确认的事实。原文引文标明来源；改写后的提示标明为产品表达。

## 4. 用户流程与页面修改

### 4.1 准备与重构中枢：让用户知道接下来要经历什么

在现有重构中枢说明三阶段各自作用：

> 晨间，写下不愿继续的生活和真正想要的生活。白天，看看实际行为在服务什么。晚间，把观察整理成明天可以尝试的方向。

保留“一日”的推荐安排，不设必须等待 24 小时的门槛。用户选择跨日继续时说明：

> 你可以分几天继续。晚间综合时，回看这次探索相关日期的观察。

入口使用“开始晨间探索”“记录日间观察”“继续晚间综合”。有草稿时显示草稿存在、最近保存时间或待保存状态；“本次方向已保存”与“草稿”明确区分。

“本次”在第一版仅指当前探索草稿，不宣称已经自动识别全部相关记录。材料归属由日期范围和用户选择确认。

### 4.2 晨间：从抽象答案走向具体生活

保留 14 问及原有题义，尤其是五年、十年、临终代价、旧身份和社交代价、三年生活画面与本周行动。可以在视觉上分组，但不合并或遗漏问题：

| 问题 | 探索作用 | 产品支持 |
|---|---|---|
| 1–4 | 看见持续不满与言行之间的距离 | 提示回忆具体场景，允许稍后补充 |
| 5–8 | 看见现有生活轨迹的长期代价 | 保留普通星期二等生活细节，不缩成“你的痛点是什么” |
| 9–11 | 看见身份、评价与自我保护 | 保留挑战性追问，允许暂时不能确认 |
| 12–14 | 描绘想建设的生活及相符行动 | 先打开愿景，再在晚间落到现实尝试 |

关键处增加简短、可收起的提示，不新增必填字段：

> 先写下你的解释。白天可以用实际发生的事情再核对它。

第 12 问保留“暂时忘掉现实可行性”的作用，不在此处提前要求证明目标可行。现实条件放到晚间的行动安排和后续反馈中考虑。

答案仍是探索原稿，不自动转成最终身份或心理诊断。结束时可以进入日间观察，也可以保存后稍后继续。提示“原稿已保存”只在保存确认成功后出现。

### 4.3 日间：用实际行为核对晨间解释

六问和追加三问保持可用。提醒开关只控制通知排程；关闭通知后，手动打开问题、查看晨稿和记录观察仍可使用。

每次进入问题，界面顺序为：

1. 当前问题。
2. 可展开的“回看晨间原稿”，保留查看全部原稿的入口。
3. 自由记录区，提示描述刚才实际发生的事情。
4. 可选的行为标签，保留“其他／待核对”，不预选“逃避”。

记录提示示例：

> 刚才发生了什么？你做了什么？它可能在满足或保护什么？

“休息”“照顾家人”“完成现实责任”不能由系统直接归为逃避。用户也可以写“暂时不知道”。

日间记录保存当前问题的标识或题干快照，晚间回顾时显示“问题 + 时间 + 用户记录”。这用于解释上下文，不能据此断言用户的动机。

通知仍直接打开对应问题；原文六个时点表述为“原文示例，可按日程调整”。送达文案描述已安排提醒，不承诺所有设备准时。

### 4.4 晚间：先回看材料，再形成暂定方向

晚间开始处提供材料回顾：

- 晨间探索原稿。
- 用户所选日期范围内的日间观察，显示日期、问题和正文。
- 可继续补记观察的入口。

默认范围建议覆盖当前晨间草稿开始日至当前日。范围可改；界面必须显示实际选中的范围，不将其中所有观察直接称为“本次专属记录”。没有可用开始日期时默认今天，并明确提供日期选择。

跨日进入时显示“观察范围：11 月 13 日—11 月 14 日”等实际日期。范围内无记录时说“这段时间尚无日间记录”，允许调整范围或继续综合；不阻止用户凭记忆思考，也不声称已完成全天观察。

保留当前 11 步，以三个视觉小组组织，避免把连续填框呈现为心理改变：

| 小组 | 当前步骤 | 修改重点 |
|---|---|---|
| 理解当前模式 | 反愿景、自我保护、内部模式 | 带回材料；允许待核对解释 |
| 选择想建设的生活 | 身份、愿景 | 身份连接生活方式，愿景可以演化 |
| 安排行动与边界 | 年目标、月项目、每日杠杆、最小启动行动、价值约束、环境规则 | 明确彼此关系，考虑现实可执行性 |

具体题干建议：

**自我保护**

> 回看今天的观察，如果某些行为是在保护自己，它们在保护什么？这种保护带来了什么，也付出了什么？

**内部模式**

> 经过这些观察，哪个反复出现的内部模式或信念，最像是在让你停留原地？

补充提示：

> 先把它作为待核对的解释。哪些观察支持它？安排下一步时，也看看时间、精力、技能和环境会怎样影响行动。

这里继续聚焦内部探索；现实条件核对作为补充，避免系统预设一切都来自内部问题。无需新增心理评估或归因评分。

**身份**

> 为了让这种生活逐渐变得自然，你想以怎样的方式生活和行动？写下你目前愿意尝试的身份表达。

补充：“它可以随经验调整，不必现在就完全做到。”

**一年目标**

> 一年后，希望有什么具体事实成立，让你看见自己正在接近想要的生活？

允许数量、成果或其他合适指标。“发布一件作品”能作为观察事实，不由系统推断它证明了全部旧模式已经消失。

**一月项目**

> 为了推进这个一年目标，这个月需要学习什么、练习什么，或做出什么成果？

**每日杠杆**

> 为了推进这个月项目，明天优先做哪 2–3 个行动？可以为每项安排一个时间块。

**最小启动行动**

> 从上面一项行动中，选出现在能开始的最小一步。

价值约束与环境规则继续分别填写。用折叠上下文展示相关上一步答案，不要求每屏展示六组件，也不要求新增结构化任务系统。

提交后展示一张可展开的方向卡：六组件完整可查看，身份、最小行动与环境规则另列。完成提示：

> 本次方向已保存。接下来，在生活中尝试，再根据反馈调整。

### 4.5 首页：把方向带到今天

首页继续突出一个最小启动行动，在其附近用一行可展开的上下文说明对应项目，例如：

> 这一步服务于：完成第一篇文章初稿。

使用当前已有方向数据。存在多个每日杠杆时，允许用户自行选择或编辑最小启动行动，不由系统根据文本推断关联。

首页保留现有中枢导航，“记录反馈”“回看／修改方向”容易找到。反愿景作为用户选择的提醒保留，视觉上不反复强化自我否定。

专注结束、行动后或用户主动打开反馈时，提供“记录这次发生了什么”的入口。完成专注只说明完成了一段专注记录，不自动表示推进了项目。

### 4.6 行动反馈：让四个框承担比较与学习

首先修复保存按钮状态。保留四字段、允许部分记录，按钮统一称“保存记录”，不把任意填写都称为“完成闭环”。

| 字段 | 提示建议 |
|---|---|
| 尝试了什么 | 这次想推进什么？做了哪一步？原本希望发生什么？ |
| 发生了什么 | 实际发生了什么？相对于原先期望，有什么差距或意外？ |
| 得到什么认识 | 哪些解释得到支持，哪些需要重看？行动方式和现实条件有什么影响？ |
| 下一次调整什么 | 下次准备保留或改变什么？可以调整行动、环境、项目，也可以重新考虑方向。 |

反馈页上方提供可展开的“当前方向”摘要，优先展示月项目与相关行动；价值约束、愿景等可进一步查看。未建立方向的用户仍可记录，不阻断。

保存后显示记录及下一次调整内容，并提供返回首页和查看当前方向的入口。先利用现有导航完成衔接，不必新增“再次尝试”专属按钮。

下一次调整不能自动覆盖首页行动，因为用户可能调整的是环境或项目。提供明确的用户操作：“修改最小启动行动”或“查看／修改方向”，由用户确认要改变的内容。

反馈记录与当前方向不同步时不误导：最小版保存一份可选的简短方向上下文快照；读取历史时标明“记录时参考的方向”。不要用今天的新目标去解释昨天的反馈。

### 4.7 回顾与统计：帮助看材料

历史方向支持查看已保存的全部六组件及额外字段。数据已存在，优先补详情展示；不要为了历史详情重做数据库。

周回顾先描述记录事实，再邀请用户观察：

> 最近 7 天，你记录了 N 次主观完全匹配。回看这些记录，哪些行动实际支持了你想建设的生活？

未记录偏离或 SOS：

> 这段时间没有相应记录。你可以结合实际经历回看。

年度内部模式：

> 当年记录的内部模式是……

避免“身份站稳”“稳定的证据”“旧信念已松动”等由计数或填写推导的结论。无需新增进步评分；允许用户自己记录可观察的变化。

### 4.8 来源与方法说明：在需要时解释

在重构中枢放一个简短“关于这套方法”入口，使用现有页面内说明或弹层即可，内容包括：

> 这套流程基于 Dan Koe 的文章：晨间探索、日间观察、晚间综合。原文建议留出一整天、使用纸笔并自主思考。ResetSelf 提供数字记录，也允许跨日继续；最小启动行动、周回顾等是产品适配或扩展。方向与身份可以在实践中调整，流程不保证对每个人产生同样效果。

提供作者、文章名称与来源链接。重要语义仍在当下页面提示，不能让用户必须读完理论说明才能开始。

## 5. 完整体验示例

以下是演示数据，不作为用户默认答案，也不要求每位用户得到相同结论。

用户晨间写“想写作，却一直搜工具”，猜测自己害怕作品被评价。日间记录“准备动笔时又研究了一个编辑器”；另一次记录“下班后疲惫，休息以后写了十分钟”。晚间看到，既有回避公开作品的可能，也有精力安排的影响。

用户将愿景写为“稳定创作并愿意让作品与读者见面”，一年目标为“发布第一组作品”，月项目为“完成并分享第一篇文章”，每日杠杆为“写提纲、补一个真实案例”，最小行动为“打开文档写一个标题”。价值约束是保护睡眠，环境规则是写作时把手机放远。

尝试后发现提纲能开始，但继续润色拖延了分享。反馈写下“下次把草稿发给一位可信任的朋友，询问是否看懂中心意思”。用户可以修改行动，继续核对评价恐惧的解释，也可以发现技能训练更关键。

验收看 App 是否支持这条路径、是否准确保存和带回材料；不能要求用户最终认定自己害怕评价。

## 6. 技术实施方案

### 6.1 保存可靠性优先

**反馈页**

`action_feedback_page.dart` 的 `_handleFieldChanged` 每次输入变化都更新页面的可保存状态。保存成功前不清空输入；失败保留内容、说明失败并允许重试。保存期间防重复提交。记录列表加载失败与“没有历史记录”分开显示。

**晨间与晚间**

保留防抖减少写入，但统一保存出口：

1. 最新编辑先保留在内存草稿中。
2. 防抖写入按顺序执行，避免旧写入覆盖新输入。
3. 普通返回、“稍后继续”、完成提交均主动提交待保存内容并等待结果；不能在 `dispose` 才尝试等待异步保存。
4. 所有必要写入成功后才能提示“已保存”。
5. 失败保留当前内容和待保存状态，提供重试；用户明确选择放弃未保存改动时才退出。

应用进入后台时尽可能提交待保存内容。操作系统强制结束进程无法靠退出回调保证；根据实际验证说明恢复能力，不宣称数据绝不丢失。

晨间 `_persist` 返回可辨识的保存结果；完成流程汇总失败，不让后续单条成功清掉前面的失败。晚间提交保持草稿和正式记录状态一致，必要的多表写入用事务。

### 6.2 跨日材料的最小实现

在仓库增加按日期范围查询日间观察的能力，替代晚间固定调用 `getTodayInterruptReflections`。使用本地日期边界，以起始日零点到结束日次日零点的半开区间查询；确认数据库现有时间存储格式后转换，不在方案阶段假定其时区。

范围默认值来自当前探索开始时间；没有可靠起点时使用今天并允许选择。UI 展示查询范围与时间。日期范围解决“找得到并能回看”，不能证明观察属于某个唯一反思批次。

当前晨间表按 `question_key` 保存一份原稿。第一版明确支持一份当前探索；再次开始时先说明会如何处理当前原稿，并保留继续现有草稿的入口。未完成归档设计前，不宣称支持多批次晨稿同时独立恢复，也不静默清空已有内容。

### 6.3 数据改动分层

| 数据 | 第一轮处理 | 理由 |
|---|---|---|
| 六组件、身份、两类行动和约束 | 沿用已有字段 | 修提示和展示即可 |
| 日间观察 | 增加可空的问题标识／题干快照 | 历史回答能解释其问题上下文 |
| 反馈 | 增加可空的简短方向上下文快照 | 方向修改后仍能理解旧记录 |
| 当前探索开始时间 | 如无可用字段，增加可空草稿元数据 | 为跨日默认范围提供依据 |
| 晚间步骤恢复 | 后续体验迭代，可保存步骤 id | 支持继续填写，不是方法硬要求 |
| 独立反思批次与关联 | 暂不强制引入 | 多批次原稿归档成为需求时再设计 |

新增字段只用于提供上下文，不能用文本存在与否判断用户已理解方法。旧日间记录缺题干时标为“未记录问题”；旧反馈缺方向时正常显示正文，不猜测归属。

若实施新增字段，按当时数据库版本增量迁移，更新模型、读写、导出与恢复。备份既要包含新字段，也要兼容旧备份缺字段；旧记录不能被强行绑定到当前新方向。

## 7. 实施顺序与每轮交付

### 第一轮：记录能可靠保存，系统不替用户断言

任务：修反馈按钮；处理晨间／晚间退出及保存失败；区分列表错误和空记录；替换已列出的统计、年度、读取错误和通知承诺文案。

交付：首次正常输入即可保存；快速返回不丢最后输入；失败不报成功；文案只陈述有证据的事实。反馈及保存路径具备必要回归测试。

这一轮先不引入新数据字段，降低迁移与交互修复耦合。

### 第二轮：晨间、日间、晚间能够互相支持

任务：日间回看晨稿；关闭提醒后可手动练习；日间问题上下文；晚间范围选择与跨日材料；晚间内部模式提示和行动关系；必要的开始时间元数据。

交付：用户能核对晨间解释、看到前一天观察，并据此形成具体行动。涉及字段的迁移和备份兼容完成验证。

### 第三轮：方向进入行动，反馈支持修正

任务：首页项目上下文；反馈四字段提示及方向快照；反馈后修改行动／方向入口；六组件历史详情；方法来源入口。

交付：用户能说明行动服务什么、比较期望与实际、保留下一次调整，并自主带回行动场景。

### 第四轮：按使用证据补便利性

可选任务：恢复晚间步骤、标记待回看问题、记录修改原因、多批次晨稿归档。

实施状态（2026-11-14）：用户授权继续后，四项均已实现。晨稿归档和恢复使用事务，先明确说明未提交晚间草稿的处理；标记与原因可选，不增加必填题。原稿历史可连同自行选择日期范围的观察回看，行动修改保留前后文本及原因。

这轮不作为前三轮方法体验交付的前置条件。只有实际出现难以继续、混淆历史或找不到材料的问题时，才扩展机制。

不在本次方案中新增等级、积分、排名、强制计时或 AI 代答。游戏隐喻通过清楚的方向、项目、行动与规则体现。

## 8. 场景验收与验证范围

| 场景 | 必须观察到的行为 |
|---|---|
| 首次反馈输入 | 任一字段输入有效文本后能保存；全部清空后禁用；再次输入仍可保存 |
| 保存失败 | 输入保留、明确失败、可重试；不显示统一成功，不形成重复记录 |
| 晨间／晚间快速退出 | 最后一次输入在成功退出后重新进入仍存在；含系统返回和“稍后继续” |
| 连续快速编辑 | 重新读取是最后输入，旧异步写入不覆盖新值 |
| 跨日综合 | 可以选前一天或多日范围，展示已存在观察及时间，不只查询今天 |
| 日间通知关闭 | 停止排程，手动问题和记录入口仍可用 |
| 问题上下文 | 新记录可回看题干；旧记录缺上下文时不编造 |
| 方向修改后看旧反馈 | 显示记录时上下文或明确缺失，不把新目标冒充旧目标 |
| 不知道动机 | 能记录不确定的解释、继续探索；不被强制归为逃避或旧惯性 |
| 行动与项目关系 | 能取得相关月项目，写出比较与下一次调整，并找到修改入口 |
| 仅写部分反馈 | 可保存，显示为记录；不宣称理解、成长或闭环完成 |
| 六组件历史详情 | 所有已保存组件可查看，价值约束与环境规则不混用 |
| 提醒通知 | Android 真机验证权限、到点、重启及冷／热启动直达；记录系统条件和结果 |
| 数据升级和备份 | 新安装、项目支持的旧版本迁移、旧备份导入、新备份往返均保留原有内容 |

自动测试集中于按钮状态、保存失败与竞态、日期边界和迁移／备份兼容；普通文案和低风险布局调整通过人工核对即可。

每轮代码修改后运行 Flutter 静态检查、适用测试与构建。最终在真机走完首次三阶段、跨日继续、修改方向与反馈、提醒开关和通知直达。原报告中静态检查、两项测试与 APK 构建通过，不能替代这些新增场景验收。

方法体验验收由任务路径判断：给用户一个实际困扰，观察他能否找到材料、作出自己的解释、形成行动并回看结果。记录卡点，不规定答案、情绪强度或心理改善。
